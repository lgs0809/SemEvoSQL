# 建模判断与问询

## 文档来源与作用

| 文档与原用途 | 用于补什么 | 不能擅自推导什么 |
|---|---|---|
| 产品／业务方参与的PRD：功能、流程、规则 | 业务对象、状态、订单退款条件 | 没写出的指标公式或跨月归属 |
| 研发技术设计：实现与读写链 | API字段落库映射、拆表、更新时点 | 过期设计自动覆盖当前结构 |
| 后端接口文档：联调字段、单位、枚举 | 对外含义、金额尺度、状态值 | 同名接口字段必等于同名物理列 |
| 数据库设计／ER／迁移：表列键关系 | 物理关联、历史拆分原因 | 无约束就根据id后缀认定唯一 |
| QA测试／验收：具体场景和边界 | 退款、取消、特殊状态示例 | 单例证明全部业务规则 |
| 操作手册：页面和用户使用方式 | 业务别名、筛选说明 | 页面值直接当原始字段 |

指标口径／报表需求不是每个软件团队必有的文档，已有则用，缺少就问关键业务定义。

## 字段映射例

物理库只有amt；接口说明paidAmount是实付金额、单位分；技术设计明确paidAmount写amt，才形成完整映射依据。只有接口说明时保留猜测，问amt含义及单位。文档元与存储分可能是转换，先核对读写，不直接宣布冲突或选一个覆盖。

## 实体粒度例

- 用户＋扩展：用户主键id、扩展uid唯一，缺失扩展也保留用户→LEFT JOIN。扩展多条先查是历史快照还是多地址；前者要有效期规则，后者可能是独立实体。v1只接有唯一依据的扩展。
- 订单明细宽表：order_id重复，item_id唯一，订单金额在每行重复。明细实体可直接映射；订单实体需去重／聚合来源规则和重复属性一致性。不可任意MAX，v1不支持时报告能力缺口。
- 主体type=CUSTOMER/SUPPLIER：确需区分可建两个带固定过滤的实体；否则统一主体加类型。身份键仍须可靠。
- 年份分表：通常需要UNION ALL并确认重叠，不是JOIN；v1不支持来源集合，别编造一种语法宣称通过。

问询以会改变结果的粒度、金额单位、时间、筛选和关联为优先。不同维度可并列问，选项须真正互斥；允许其他／暂不确定。已确认项除非资料或含义变化不重复问。

## 指标例

“支付金额”需确定金额字段、成功状态、时间归属、单位、退款是否影响。按订单明细关联可能重复金额；指标本身SUM正确也不能抵消JOIN放大。初始化确认这些规则并保存证据，系统查询阶段继续检查粒度。

初始化后用户新提出有效获客成本这样的复合定义，属于产品内运行时问询和语义进化，不要求每次再跑本Skill，也不把全部聊天重新交给Codex。
