# 审计维度
## ✅ 维度 1：语义一致性 (Semantic)
目标对齐：SQL 是否查询了 上面提到的【当前执行指令】 中要求的表和字段？
过滤准确：是否遗漏了 上面提到的【当前执行指令】 中明确要求的 WHERE 条件（如时间、状态）？
聚合正确：GROUP BY 和聚合函数（SUM/COUNT）是否符合 上面提到的【当前执行指令】 意图？
指标口径：SQL 是否严格使用 Semantic Blueprint 中已解析的指标表达式和过滤条件？不得自行替换或发明公式。
粒度与 Join：SQL 是否遵守模型 Grain、发布关系和 Cardinality？若 `preAggregationModelCodes` 非空，是否先聚合后 JOIN，避免 Fan-out？
业务规则：SQL 是否应用了计划中的强制规则，且没有使用外部证据覆盖正式定义？
NULL 语义：Catalog 中 `nullable=true` 只是事实，不是自动过滤规则。不要要求所有 nullable 字段都 `IS NOT NULL`。若当前步骤明确要求连续/有序时间序列、LAG/LEAD、同比环比等，应结合具体时间字段判断 NULL bucket 是否会破坏当前步骤；若用户明确查询未支付、缺失时间或 NULL 分布，则保留 NULL 是正确的。多时间字段分别判断，不得套用一个全局时间规则。
对时间 bucket、窗口排序或周期比较使用的受治理时间轴，若用户没有要求把缺失时间当作业务类别，`time_column IS NOT NULL` 是防止 NULL bucket 破坏排序/比较的执行层完整性保护，不是擅自新增时间范围或业务过滤，不得因此判定不通过。
排序 NULL 事实必须按当前方言判断：MySQL 默认升序时 NULL 在前、降序时 NULL 在后；PostgreSQL 默认升序时 NULL 在后、降序时 NULL 在前（可用 `NULLS LAST`）。不得使用相反的方言规则制造虚假逻辑错误。
注意：如果指令只要求“查询北京”，而 SQL 没查“上海”，这是通过的。

## 维度 2：结构正确性 (Syntax & Schema)
幻觉检测：SQL 中的所有表名和列名是否都能在【数据库 Schema】中找到？(大小写不敏感，但拼写必须正确)。
方言兼容：是否使用了符合 {dialect} 的语法（例如日期的处理、引号的使用）。只判断实际正确性，不要因为你偏好另一种等价实现而判失败。对于月/周等时间 bucket，只要表达式在当前方言中确定、分组语义正确、窗口排序能保持真实时间顺序，就应接受；除非当前执行步骤明确要求某一种展示格式，否则不要强制“周起始日期”等唯一表示法。

# 判定标准
## 不通过
查询了 Schema 中不存在的幻觉字段。
逻辑与指令或业务参考信息冲突。
遗漏了指令中的核心过滤条件（导致数据量暴增）。
聚合维度与指令要求不符。
存在明显的 SQL 语法错误。

## 通过
逻辑正确，字段存在。
包含非核心的排序差异（允许）。
包含多余的 ID 列（允许，通常为了后续 Join）。
包含符合业务定义的特定过滤条件（即使指令中未详述，但在 Evidence 中有定义）。
